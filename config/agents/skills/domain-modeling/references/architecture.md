# Application Architecture (Functional Core, Imperative Shell)

ドメインモデルを最大限に活かすアプリケーションの組み立て方。原則: モデル（型 + 純粋関数）が中心、副作用は薄いシェルに隔離、依存は関数型ポートで内向き。

## 1. 全体像

すべてのユースケースは次の一本道に正規化できる:

```text
入力 (unknown)
  → parse（境界で一度だけ）        … Shell（入口アダプタ）
  → 読む: 状態・関連データのロード  … Shell (I/O)
  → 決める: ワークフロー            … Core（純粋関数）
  → 書く: 永続化・イベント発行      … Shell (I/O)
  → 応答
```

- この一本道は1つの境界づけられたコンテキスト（モジュール）の内部構造。システム全体はコンテキストの集合であり、コンテキスト間の関係はコンテキストマップで決める
- ヘキサゴナル・オニオン・クリーンは本質的に同一（依存を内向きに、ドメインを中心に）。関数型ではレイヤ規約で守らなくても「core を純粋に保つ」だけでこの構造が型により強制される
- **core に置いてよいもの**: 型定義と純粋関数のみ。I/O・現在時刻・乱数・ログ・フレームワークや ORM の型は置かない。検証スキーマ（zod 等）は検証ルールを不変値として表現した純粋なデータなので core に置いてよい
- 時刻・ID 生成が要る決定は、値を引数で受け取る（`now: Date`、`newId: OrderId`）。呼ぶのはシェル

## 2. 依存の向きと合成ルート

ポート = 関数型。class も DI コンテナも不要。

```typescript
import { ResultAsync } from "neverthrow";

type LoadOrder = (id: OrderId) => ResultAsync<OrderState, LoadOrderError>;
type SaveOrderEvents = (
  events: ReadonlyArray<OrderEvent>,
) => ResultAsync<void, SaveError>;
```

- ハンドラはポート型にのみ依存する。ドメインはポートを知らず、値だけを受け取る。アダプタ（PG 実装・外部 API クライアント）がポート型を満たす
- 結線は合成ルート（`main.ts` / エントリポイント）の1箇所だけ:

```typescript
const orderRepo = createPgOrderRepository(pool);
const handlePlaceOrder = placeOrderHandler({
  loadOrder: orderRepo.load,
  saveOrderEvents: orderRepo.saveEvents,
  now: () => new Date(),
});
```

- フレームワーク（Hono / Express / axum / net/http）はシェルの一部。ルーティング層 = 入口アダプタで、境界スキーマの parse・ハンドラ呼び出し・応答への変換だけの薄い皮に保つ

## 3. 垂直スライスのディレクトリ構成

レイヤ横断の水平分割（controllers/ services/ repositories/）ではなく、業務領域 → ワークフロー単位の縦割り:

```text
src/
├── order/                        # 業務領域（モジュール）
│   ├── domain/                   # Functional Core: 型と純粋関数のみ
│   │   ├── order.ts              # 状態機械 (UnpaidOrder | PaidOrder | ...) と遷移関数
│   │   ├── order-line.ts         # 値オブジェクト
│   │   ├── events.ts             # OrderEvent 直和型
│   │   └── place-order.ts        # ワークフロー: (Command, State) -> Result<Event[], Error>
│   ├── ports.ts                  # LoadOrder / SaveOrderEvents などの関数型
│   ├── handlers/                 # Imperative Shell: 読む → 決める → 書く
│   │   └── place-order.handler.ts
│   └── infra/                    # アダプタ: ポート実装
│       ├── order-repository.pg.ts
│       └── order-row.ts          # DB 行型 ⇔ ドメイン型のマッピング
└── main.ts                       # 合成ルート
```

- 変更は通常1ワークフロー（1スライス）に閉じる。機能追加 = スライス追加
- モジュール間は絞った公開 API かドメインイベント経由でのみ連携する。他モジュールの `domain/` を直接 import しない
- モジュール境界は境界づけられたコンテキスト（語彙が変わる場所）と揃える。跨ぐ変更が頻発するなら境界を疑う

## 4. ハンドラの標準形 (Impureim Sandwich)

すべてのハンドラは「読む → 決める → 書く」に組む:

```typescript
const placeOrderHandler =
  (
    deps: Readonly<{
      loadOrder: LoadOrder;
      saveOrderEvents: SaveOrderEvents;
      now: () => Date;
    }>,
  ) =>
  (
    command: PlaceOrderCommand,
  ): ResultAsync<PlaceOrderResponse, PlaceOrderError | InfraError> =>
    deps
      .loadOrder(command.orderId)
      .andThen((state) =>
        placeOrder(command, state, deps.now()).asyncAndThen((events) =>
          deps.saveOrderEvents(events).map(() => toResponse(events)),
        ),
      );
```

- 「読む」を全部先に、「書く」を全部後に。**純粋な決定の途中に I/O を挟みたくなったら、ワークフローを2段に分割するサイン**
- ポートをドメイン関数に注入して core から I/O を呼び戻さない。条件付きロードが必要なら、読む範囲を広げて値で渡すか、ワークフローを分ける
- ハンドラ自体はロジックを持たない。持ち始めたらそれはドメインの決定であり、core へ移す
- ハンドラは parse 済みのコマンド型を受け取る。`unknown` を受けて境界スキーマで parse するのは入口アダプタの仕事（patterns.md 境界での parse）

## 5. 永続化とリポジトリ

リポジトリ = **ドメインモデルを正本とする永続化の抽象**。DB は正本の一表現にすぎず、モデルの完全性はドメイン型が担う。関数型ではコレクション比喩と ORM 機構を捨て、契約だけを残す。

**リポジトリの契約（5法則）**:

1. **集約単位** — ロード / セーブの粒度は常に集約全体。部分ロード・部分更新を提供しない
2. **ドメイン型のみ** — 入出力はドメイン型。ORM モデル・行型・スキーマ生成型をドメイン層に漏らさない。モデルとテーブルは 1:1 でなくてよい（型の合成で分割し、マッピングで吸収する）
3. **load = parse** — DB から読んだ値も信頼境界の外。集約・状態の schema で parse して Always-Valid な集約として復元し、失敗は Result で返す（自分の DB に対する腐敗防止層）
4. **save = 全体置換** — イミュータブルなモデルに変更追跡は存在しないため、save は「集約全体の原子的置換」または「イベントの追記」。ORM の dirty-tracking / Unit of Work は不要になる
5. **クエリを持たない** — 検索・一覧はリポジトリに生やさず読み取りパス（§6）へ。リポジトリは書き込みモデル専用

マッピング層は「汚さの収容所」として設計されている。インピーダンスミスマッチ（NULL 分岐・kind ディスパッチ・命名変換・ドライバ固有型）はここに集約する。ただし3つの規律:

- **嘘を押し込まない** — 不正データの黙殺・デフォルト値での補正は汚さの吸収ではなく捏造。検証結果は `CorruptRow` のような Result で正直に申告する
- **賢くならない** — 業務判断が混ざったら decide の漏出。マッピングの仕事は同型変換と検証のみ
- **テストで買い戻す** — 型保証が最も弱い場所なので、save → load の往復が恒等であることを実 DB の統合テストで守る

実装形は「ポートの束 + ファクトリ」:

```typescript
type OrderRepository = Readonly<{
  load: (id: OrderId) => ResultAsync<Order, LoadOrderError>;
  save: (
    order: Order,
    expectedVersion: Version,
  ) => ResultAsync<void, SaveOrderError>;
}>;

const createPgOrderRepository = (pool: Pool): OrderRepository => ({
  load: (id) =>
    selectOrderRow(pool, id).andThen((row) =>
      Order.fromRow(row).mapErr(toLoadError),
    ),
  save: (order, expectedVersion) =>
    upsertOrderRow(pool, OrderRow.from(order), expectedVersion),
});
```

**メソッド面は教義ではない** — `load` / `save` は最小形であって上限ではない。契約（5法則）を守る範囲で、ワークフローが要求する能力とエラー意味論に合わせて増やす:

- **不在の意味論で分ける**: `find`（不在が正常 → `Result<Order | null, IoError>`）と `load`（不在がエラー → `Result<Order, NotFound | IoError>`）は別の能力。呼び出し側のワークフローがどちらを期待するかで選ぶ
- **エラー意味論で分ける**: `create`（重複が業務エラー: `AlreadyExists`）と `update`（競合が業務エラー: `VersionConflict`、expectedVersion 必須）の分離は「予期されるエラーを戻り値型に現す」原則の帰結。何でも受ける `save` 1本に統合するとエラー型の精度が落ちる。upsert 意味論が自然なストア（ドキュメント / KV / イベント追記）では `save` 1本でよい
- Tx をリポジトリ内に閉じたい場合は `update: (id, decide: (order: Order) => Result<Order, E>) => ...` の関数受け取り形も有効（load → 純粋な decide → save を1Txで包む。FCIS と両立する）
- 増やしてよいのは書き込みモデルの能力だけ。検索・一覧が混ざり始めたら法則5違反（リードモデルへ）

### upsert（あれば更新・なければ作成）の扱い

upsert には出自の異なる2種類があり、混同すると事前条件の放棄になる:

- **業務の意味論としての upsert** — 「以前存在したか」が業務語彙に存在しない（設定保存・スナップショット同期・冪等な受領記録・プロジェクション反映）。正当な表現
- **実装都合の upsert** — 業務は初回と変更を区別しているのにコードパスを1本にしたいだけ。`AlreadyExists` / `VersionConflict` の型が消え、lost update の入口。禁止

リトマス試験は発見フェーズで済んでいる: **ドメインイベントが1つ（〜が保存された）なら upsert、2つ（〜が登録された / 〜が変更された）なら create / update**。

| 関心                              | 置き場所                                                                                        |
| --------------------------------- | ----------------------------------------------------------------------------------------------- |
| 判定（upsert か否か）             | 発見フェーズ（イベントの数）                                                                    |
| 宣言                              | ポートの型。エラー型に AlreadyExists / VersionConflict が現れないこと自体が upsert 意味論の宣言 |
| 業務的な分岐（あればX なければY） | core。load が不在許容の型で返し、純粋関数が分岐して別のイベントを返す                           |
| 原子性の機構                      | マッピング層（`INSERT ... ON CONFLICT` / conditional write）                                    |

- **ハンドラでの「存在チェック → if で create / update を呼び分け」は禁止**（check-then-act の TOCTOU 競合）。原子性はストアの単一文でしか保証できない。core で分岐する場合も、競合時の `AlreadyExists` は Result で受けて再読込・リトライする（unique 制約が最終審級）
- upsert でも並行編集の後勝ち（last-write-wins）が許されないなら expectedVersion が要る — それはもう update である

永続化戦略は契約を守ったまま3択から選ぶ:

| 戦略         | save の形                                     | 向き                                                            |
| ------------ | --------------------------------------------- | --------------------------------------------------------------- |
| 行マッピング | 集約 ⇔ 正規化テーブル群への変換               | 既存 RDB 資産・SQL での分析が必要なとき                         |
| ドキュメント | 集約1つ = 1レコード（jsonb 等）+ バージョン列 | 「モデル = 正本」を最も素直に永続化。クエリはリードモデルで補う |
| イベント追記 | Decider の出力イベントを append               | 履歴自体が業務価値を持つ・イベントソーシングまで行く場合        |

- **トランザクション境界 = 1集約 = 1ハンドラ**。トランザクション制御はシェル（ハンドラ / リポジトリ）に置き、core は存在を知らない
- 集約の保存とイベント発行に原子性が要るなら Transactional Outbox（同一 Tx で outbox テーブルに書き、非同期で配送）
- 同時更新は楽観ロック（バージョン列）で検出し、競合は予期される業務エラーとして Result で返す

### 状態機械の永続化（直和型のマッピング）

リレーショナルモデルに直和型は存在しない。この不整合を吸収するのがマッピング層の主戦場:

| 方式                   | 形                                                                                          | 特徴                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 単一テーブル + kind 列 | 状態依存の列は NULL 許容にし、CHECK 制約（kind='Paid' → paid_at IS NOT NULL）で部分的に守る | 最も一般的。DB の保証は部分的なので load 時の parse が最終防衛線            |
| jsonb ドキュメント     | 直和型をそのままシリアライズ + バージョン列                                                 | 状態依存フィールドの不整合が構造的に発生しない。「モデル = 正本」に最も忠実 |
| 状態ごとにテーブル     | 状態遷移 = 行の移動                                                                         | DB 側の保証は最強だが遷移とクエリが重い。状態数が少ない場合のみ             |
| イベント追記           | 状態は保存せず `evolve` で導出                                                              | イベントソーシングの形。状態機械の遷移がそのまま永続化の単位になる          |

復元は「kind で分岐 → 状態ごとの必須フィールドを検証 → 対応するバリアントへ」。DB が直和を表現できない以上、**load 時の網羅的 parse が型保証を永続化を跨いで維持する唯一の手段**になる。状態の union schema（discriminatedUnion）がこの分岐と検証をそのまま実装する（patterns.md 状態機械）:

```typescript
const orderFromRow = (row: OrderRow): Result<Order, MappingError> => {
  const result = orderSchema.safeParse({
    kind: row.kind,
    id: row.id,
    lines: row.lines,
    paidAt: row.paid_at ?? undefined, // 形変換: 命名・NULL → undefined
    trackingId: row.tracking_id ?? undefined,
  });
  return result.success
    ? ok(result.data as Order)
    : err({ type: "CorruptRow", id: row.id, issues: result.error.issues });
};
```

save 側も match で各バリアントを対応する表現へ写す。網羅性チェックにより「状態を追加したのにマッピングを忘れた」がコンパイルエラーとして検出される — 状態機械の変更が永続化層まで型で伝搬する。

### ID の発行

**型と発行の抽象はドメインが所有し、生成はシェルが実行し、core へは値として渡す**（`now: Date` と同型。乱数生成は副作用）:

```typescript
type NewOrderId = () => OrderId;
```

- **DB 採番（auto-increment）は既定で避ける**。理由は4つ:
  1. Always-Valid との衝突 — ID が save 後にしか存在せず、「同一性を持たない不完全な集約」（`id: number | null`）が生まれる
  2. イベントとの衝突 — 集約は保存前にイベントを生成するため、イベントが自分の集約 ID を参照できない
  3. テスタビリティ — ID 発行が DB ラウンドトリップに縛られる。ポートなら固定値で差し替えるだけ
  4. セキュリティ — 連番は総数・成長率の漏洩と IDOR 列挙攻撃の入口
- 既定は **UUIDv7 / ULID のアプリ発行**（RFC 9562）。時間順ソート可能なのでインデックス局所性の問題も解消済み
- クライアント発行も選択肢: リトライ時の二重作成が `AlreadyExists` に化け、冪等性キーが構造的に手に入る。当然「信頼できない入力」として境界で parse する
- **技術 ID と業務 ID を分離する** — 「請求書番号は連番」のような要件は業務 ID（欠番可否・年度リセット等のルールを持つ値オブジェクト + 専用の採番ワークフロー）の話であり、技術 ID（UUIDv7、外部に見せない）と混同しない

## 6. 読み書きの分離 (CQRS)

CQRS の原義（Greg Young）は「書き込み用と読み取り用で別のモデルを用いる」— それだけである。適用は段階で捉える:

| 段階 | 内容                                                                                | 位置づけ                                                                                   |
| ---- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 0    | 分離なし。読みも書きも同じモデル経由                                                | 小規模ならこれで足りる                                                                     |
| 1    | モデル分離のみ。同一ストア、書き込みはドメインモデル経由、読み取りは SQL → DTO 直行 | 原義の CQRS の最小形。**本 Skill の既定**                                                  |
| 2    | 読み取り専用モデル / ストアを分離し、プロジェクションで同期                         | 流布している「CQRS」のイメージはここ。複雑さ・スケール・監査要件が正当化する場合にのみ採用 |
| 3    | 段階2 + イベントソーシング                                                          | 履歴自体が業務価値を持つ場合                                                               |

ドメインモデルは**書き込み（不変条件の保護）のための道具**。読み取りは状態を変えないので、ドメインモデルを経由させない。

- 書き込みパス: `parse → ワークフロー → 集約の保存`。必ず core を通す
- 読み取りパス: `クエリ → DTO 直接構築`。SQL の JOIN・ビューを自由に使い、集約を復元して詰め替えない
- 読み取り用の型（DTO）はドメイン型と別に定義してよい。画面・API の形は表示の関心であり、不変条件の関心ではない
- 段階3 まで行く場合も `decide: (command, state) => events` / `evolve: (state, event) => state` の純関数ペア（Decider パターン）で core はそのまま使える

## 7. ドメインイベントの配線

- 集約・ワークフローはイベントを返すだけで、誰が購読するかを知らない
- 同一モジュール内の後続処理: コミット後にインプロセスで dispatch する
- モジュールを跨ぐ連携: outbox → メッセージング。跨ぎの整合性は結果整合性を受け入れる
- イベントハンドラ自体も「読む → 決める → 書く」で書く（小さなワークフロー）
- イベントへの単発の反応（イベント → 次のコマンド発行）は、イベントハンドラ（ポリシー）で足りる
- 複数ステップ・補償を要する長期プロセスは Process Manager（EIP。Saga とも）— 進行状態を持つ購読者。それ自体を「状態機械の集約 + イベント購読 + コマンド発行」として、既存の部品だけで組む
- 補償は取り消しではなく逆向きの業務操作（返金・在庫戻し）。ロールバックできない結果整合の世界の undo は業務語彙で設計する

## 8. テスト戦略

| 対象                 | 手法                                                                                |
| -------------------- | ----------------------------------------------------------------------------------- |
| 型で排除した不正     | テスト不要（コンパイルが証明）                                                      |
| smart constructor    | 境界値の単体テスト                                                                  |
| ワークフロー (core)  | 純粋関数の単体テスト + Property-Based Testing。引数と戻り値だけで完結し、モック不要 |
| ハンドラ (shell)     | ポートを素の関数で差し替えた薄いテスト                                              |
| リポジトリ (adapter) | 実 DB に対する統合テスト（マッピングの往復を確認）                                  |

- テストの重心は自然と「core の単体テストが大半、shell は薄く」になる
- モックライブラリは不要。ポートが関数なので手書きの差し替えで足りる
- テストが書きにくい場所は設計の問題（core に I/O が混ざっている、決定がシェルに漏れている）を疑う

## 9. アンチパターン集

境界系のアンチパターン（分散モノリス・共有ドメインモデル等）は bounded-context.md、モデル系は patterns.md を参照。

| アンチパターン           | 症状                                                              | 処方                                                                               |
| ------------------------ | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| ロジックを持つハンドラ   | ハンドラに if・計算が増えていく                                   | 決定は core のワークフローへ。ハンドラは読む → 決める → 書くの配線だけ             |
| 決定の途中の I/O         | ワークフロー途中で条件付きロード・API 呼び出しをしたくなる        | 読む範囲を広げて値で渡すか、ワークフローを2段に分割                                |
| デュアルライト           | DB 保存とイベント発行を別トランザクションで行い、片方だけ失敗する | Transactional Outbox（同一 Tx で記録、コミット後に配送）                           |
| 1 Tx で複数集約          | 集約 A と B を同時更新して整合を取ろうとする                      | 1 Tx = 1 集約。跨ぐ整合性はイベント + 結果整合性                                   |
| check-then-act           | 存在チェック → if → create / update の呼び分け（TOCTOU 競合）     | 原子性はストアの単一文（`ON CONFLICT` / conditional write）。unique 制約が最終審級 |
| 実装都合の upsert        | `AlreadyExists` / `VersionConflict` がエラー型から消える          | 業務がイベント2つ（登録 / 変更）を区別するなら create / update に分離              |
| リポジトリへのクエリ混入 | `findByStatus`・一覧・集計がリポジトリに生える                    | 読み取りパスへ（CQRS 段階1）。リポジトリは書き込みモデル専用                       |
| 読み取りでの集約復元     | 一覧表示のために集約を load して DTO に詰め替える                 | クエリ → DTO 直行。SQL の JOIN・ビューを自由に使う                                 |
| DB 採番 ID               | `id: number \| null` の不完全な集約が生まれる                     | UUIDv7 / ULID のアプリ発行。技術 ID と業務 ID を分離                               |
| 合成ルートの散逸         | 結線・インスタンス化がコードのあちこちに散る                      | 結線はエントリポイント1箇所のみ                                                    |
