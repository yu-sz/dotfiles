## 1. 前提

- どのコンテキストの中の作業かを確認してから発見に入る
- 境界や接続に触る作業だけがコンテキストマップを要求する。マップが無ければ、触る範囲だけ現状から起こす
- 境界・接続・分類を変えたら、分類表とマップも更新する

## 2. Discovery: イベントから始める

名詞（エンティティ）抽出から始めない。名詞起点は貧血モデルと「実在しない概念のモデル化」を招く。

### 手順

1. **ドメインイベントを列挙** — 「〜された」（過去形の事実）を時系列に並べる。例: `注文が確定された` `在庫が引き当てられた` `出荷が完了された`
2. **コマンドを対にする** — 各イベントに、それを引き起こす命令（「〜する」）を置く。この対がワークフロー `(Command, State) -> Result<Event[], Error>` の入力と出力を定める。例: `注文を確定する` → `注文が確定された`
3. **コマンドの発行者を特定する** — 誰が / 何が発行するか（人・外部システム・時刻・他コンテキストのイベント）。発行者の種別が入口の実装形（ハンドラ・キュー購読・ジョブ）を決める
4. **答えられない問いと、答えが食い違う箇所を記録する** — 答えられないのは未言語化のルール、食い違うのは境界のシグナル。その場で解決しない
5. **イベントの塊から境界と集約を見出す** — 密に連鎖するイベント群が1つの境界づけられたコンテキスト（モジュール）・集約の候補

手順の源流は EventStorming（Brandolini）— 関係者との協働セッションとして行う形が原型。

### 語彙を定める

業務用語は所与ではない。全ての語をコマンドかイベントかに定め、曖昧な語は再定義してモデルの言語にする — 語彙の決定がそのまま型の決定になる。

- 「〜指示」はコマンド、「〜完了」はイベント。業務用語がコマンド / イベントを混同している場合は事実ベースの語彙に再定義する（例: 「出荷指示」→ イベントとしては「引当が完了された」）
- この区別がそのまま `Command` 型と `Event` 型の直和型になる

### 不変条件の発見

見つけ方は問いの形で選ぶ。最初の4つは業務の側から制約を掘り、最後の1つはモデルの側から漏れを検算する:

- **状態 × イベントの表を書く** — 空欄が禁止遷移。図では描かれない無効遷移が機械的に列挙される（状態遷移表、ISTQB）
- **操作の前後で保存されるものを問う** — 合計・件数・順序など、変換をまたいで変わらないものが不変条件（PBT のプロパティパターン、Wlaschin / Hughes）
- **データ破壊駆動で問う** — どうすれば壊せるか、許してはならない操作は何か（ミノ駆動。学術上の系譜は misuse case, Sindre & Opdahl）
- **ルールと具体例を往復する** — このルールの例は? この例のルールは? 詰まった箇所が未発見の制約（Example Mapping、Wynne）
- **モデルが許す値を業務に照らす** — 「ルールは何か」ではなく「この値はありえるか」と問う。業務が「ありえない」と答えた値の1つ1つが、まだ型に書いていない制約の物証（Alloy の分析プロセス、Jackson）

見つけた制約は関門を通す: 1トランザクション内で即時一貫が必要なものだけが不変条件（守り手は型・smart constructor・集約）。集約を跨ぐものは不変条件ではなく、境界設計と結果整合の判断に送る（true invariant、Vernon）

### ワークフロー分割

見つけたコマンドを、そのまま分割の単位として使う。データの形で切り直さない。

- 業務の変更は「注文確定のルールを変えたい」というプロセスの語で届く。コマンド単位なら変更が1スライスに閉じ、データ単位では複数のエンティティとレイヤに散る
- 1ワークフロー = 1関数 = 1垂直スライス — 業務語が関数名・ディレクトリ名まで同じ粒で貫通する

## 3. 記述: ドメイン記法ミニ言語

型を書く前に、ドメインを中間記法で下書きする（DMMF 記法）。コードより安く直せて、型定義にほぼ 1:1 で写せる。

```text
data 未検証の注文 = 顧客情報 AND 注文行リスト
data 注文 = 未払い注文 OR 支払済み注文 OR 出荷済み注文
data 支払済み注文 = 注文ID AND 注文行リスト AND 支払日時

workflow 注文を確定する =
  入力: 未検証の注文
  出力: 「注文が確定された」イベント OR 確定エラー
  手順: 検証 -> 価格計算 -> 確定
```

- `AND` = 直積（オブジェクト / struct）、`OR` = 直和（union / enum）、`->` = 関数
- 制約は注記で書く: `data 注文行リスト = 注文行 の非空リスト（最大100行）`
- 認識合わせと手直しはこのスケッチ段階で済ませ、それから型に写す

## 4. 集約境界の決め方

1. **トランザクションで考える** — 「1回の業務操作で同時に整合しなければならないデータは何か」が最良のヒューリスティック
2. **真の不変条件か疑う** — 「注文合計は与信枠以内」は真の不変条件か、それとも数秒の遅延が許される業務ルールか。後者なら集約を分けて結果整合性にする
3. **小さく始める** — 迷ったら集約 = 1エンティティから始め、真の不変条件が見つかったときだけ拡げる
4. **ID 参照を貫く** — 集約間はオブジェクト参照でなく ID。ロード・保存は集約単位
5. **同時更新を想像する** — 複数ユーザーが同時に触ってロック競合する設計なら境界が大きすぎる

## 5. 反復の心得

- モデルは問題解決のために選んだ切り口。同じ現実でも問題が違えばモデルは変わる
- 最初のモデリングはタイムボックスを切る（2時間で仮説を出す）。完璧を待たず実装からのフィードバックで壊して進化させる
- 型を変えるとコンパイラが影響範囲を全部教えてくれる。これが関数型ドメインモデリングにおける「進化させる勇気」の担保
- どう境界を切っても複雑さの総量は変わらない（ローカルな複雑さとグローバルな複雑さの交換）。「どちらの複雑さなら扱えるか」で選ぶ
- モデル（型定義・イベント列・ミニ言語スケッチ）は人間と AI の共有仕様書になる。実装を AI に任せる場合ほど、型と不変条件を先に固める価値が上がる
