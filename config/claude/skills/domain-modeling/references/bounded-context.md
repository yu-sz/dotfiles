## 1. 原理

- モデルは目的ごとの認識の構築物。唯一の統一モデルは存在しない
- 型の保証は境界の内側でのみ働く。モデルが通用する範囲の外では、不変条件も smart constructor も成立しない。境界の確定は型設計に先行する
- 変更の影響範囲は境界と一致する。境界を跨ぐ変更が頻発するなら、誤っているのはコードではなく境界

## 2. 境界の見つけ方

| ヒューリスティック     | 内容                                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------------- |
| 語彙の変化             | 同じ語の意味・属性・関心が変わる場所が境界。「商品」がカタログでは説明と画像、在庫では数量と棚位置になる |
| イベントの塊           | 密に連鎖するドメインイベント群は同一コンテキストの候補（process.md のイベント発見と接続）                |
| トランザクション独立性 | 境界を跨いで強整合性（同一 Tx）が必要になるなら、その境界は間違っている                                  |
| 変更理由の一致         | 一緒に変更されるものは同じ境界へ、独立に変更されるものは別の境界へ                                       |
| チームの担当           | 1つの境界は1チームが所有できるサイズに。複数チームが同じモデルを触る構造は境界の欠如                     |

迷ったら**大きめに切って後で分割する**。細かすぎる境界は分散モノリスに至り、粗い境界（モジュラーモノリス）よりはるかに直しにくい。

## 3. 境界の実装（モジュール）

1コンテキスト = 1モジュール（ディレクトリ）= 型の可視範囲として実装する。

```text
src/
├── sales/                  # 販売コンテキスト
│   ├── domain/             # この境界の中でだけ有効なモデル
│   ├── contract.ts         # 契約型（公開された言語の実装）と公開 API のみ export
│   └── ...
├── billing/                # 請求コンテキスト
│   └── ...                 # sales/domain/ は import されない
└── shared/                 # 共有してよいのは汎用の値のみ（Money, Email 等の一般概念）
```

- 境界の公開面は、絞った API（ハンドラ・クエリ関数）と契約型（DTO）に限る — ドメイン型は含めない
- コードへの越境は import の機械的禁止で塞ぐ: TypeScript は eslint の boundaries / no-restricted-imports、Go は `internal/`、Rust は `pub(crate)` / workspace 分割
- データへの越境は書き込み口の限定で塞ぐ: 永続化状態を作成・変更するのは所有コンテキストのリポジトリのみ
- 他コンテキストへ依存するときは、相手の契約型と公開 API だけを import する — これが唯一の正当な越境
- `shared/` に置いてよいのは業務的に意味が不変な汎用概念（Money・Email 等）だけ。業務モデルを共有し始めたら境界崩壊のサイン

## 4. コンテキスト間の関係と連携

コンテキスト間の依存関係の接続は、必ず以下のいずれかに分類される。暗黙の相互依存にしない:

| パターン                            | 定義                                                            | 使いどころ                                                              |
| ----------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 公開された言語 (Published Language) | 上流が公開し、後方互換を維持する契約型                          | 既定。すべての公開 API・公開イベントに適用する                          |
| 腐敗防止層 (Anti-Corruption Layer)  | 上流の契約を自分のドメイン型へ parse する変換層。下流が所有する | 上流を制御できない・上流モデルが汚染源になるとき（外部 SaaS・レガシー） |
| 順応者 (Conformist)                 | 下流が上流の契約をそのまま受け入れる                            | 変換コストに見合う差異がないとき。ただしドメイン型への波及は禁止        |
| 共有カーネル (Shared Kernel)        | 複数コンテキストがモデルの一部を共有する                        | 原則避ける。許すのは汎用の値（Money・Email 等）のみ（§3 の `shared/`）  |
| 別々の道 (Separate Ways)            | 統合しない                                                      | 連携の価値が統合コストを下回るとき                                      |

連携の実装既定:

- 既定はドメインイベントによる非同期連携。イベントは集約の保存と同一トランザクションで Transactional Outbox に記録し、コミット後に配送する。境界を跨ぐ整合性は結果整合性とする
- 最新の状態が必要な参照は、相手の公開クエリ API を呼び、契約型で受け取る
- 契約型は後方互換を守って進化させる（フィールド追加は可、意味変更・削除は破壊的変更として扱う）

## 5. 変換（腐敗防止層）

境界を跨いだ値は、形の型（契約型）はあっても意味の上では `unknown` — 自分の smart constructor で型付けし直す。Parse, don't validate は外部 API だけでなくコンテキスト間にも適用する。

```typescript
import { Result } from "neverthrow";

type SalesOrderDto = Readonly<{
  orderId: string;
  total: number;
  customerId: string;
}>;

const toBillingCharge = (
  dto: SalesOrderDto,
): Result<BillingCharge, TranslationError> =>
  Result.combine([
    ChargeId.parse(dto.orderId),
    Money.parse(dto.total),
    AccountId.parse(dto.customerId),
  ]).map(([id, amount, accountId]) => ({ id, amount, accountId }));
```

- 変換関数は**受け取る側が所有する**。相手のモデル変更から自分のドメインを守る防波堤（腐敗防止層）
- 変換に失敗したイベント・データは業務エラーとして扱い、握りつぶさない

## 6. アンチパターン

| アンチパターン     | 症状                                                    | 処方                                                           |
| ------------------ | ------------------------------------------------------- | -------------------------------------------------------------- |
| 共有ドメインモデル | 複数コンテキストが同じドメイン型を import している      | 公開契約型に置き換え、受け取る側が自分の型に parse             |
| 神モデル           | 全用途の属性を持つ巨大な `Customer` / `Product`         | コンテキストごとに別の型として定義し直す                       |
| 分散モノリス       | 境界を跨ぐ同期呼び出しの連鎖・共有 DB・同時リリース強制 | イベント連携 + データ所有の分離。境界を粗く切り直す            |
| 早すぎる細分化     | 最初からマイクロサービス的に細かく境界を切る            | モジュラーモノリスの粗い境界から始めて分割は後で               |
| 暗黙の境界         | ディレクトリはあるが型も DB も自由に相互参照            | 越境 import の機械的禁止・永続化の書き込み口をリポジトリに限定 |
